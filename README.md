# dsh-host-sl

DSH 宿主插件：**实时维护一张「谁有没做完的事」的表，dsh 崩溃或重启后自动把这些会话冷恢复唤醒**。

不需要人敲任何命令、不需要在重启前做任何准备 —— 会话在跑就自动进表，跑完自动出表，
下次进程起来时按表把它们叫回来并附上断点信息。

- 状态：**v0.7.4**，离线自测 **121 用例全绿**（见「自测」）
  （v0.7.1 = 注入文案改为固定首句 `sl已接续会话,继续`；v0.7.2 = **子代理接续结果回报给父会话，成功也报**；
  v0.7.3 = 那条通知**改走 `steer` 插队**（正常情况下同一轮内可见）；v0.7.4 = 按第二轮复核修掉两条 P2：
  **不再裸唤醒"自己有条目"的父会话**（否则让位的那条会永久丢掉续跑注入）、**插队前先看 next-turn 是否清空**
  （否则结果通知会跑到续跑指令前面），并把预告改成与通知同源）
- 旧版（v0.6.0 的「`/sl` 命令 + Markdown 交接记录 + `pending.json`」那套）的完整文档**不随本仓库分发**
  （作者本机留档）—— 那一套机制在 v0.7.0 里已整体删除
- 设计依据（宿主源码逐条核实）：见下面「为什么这么设计」与 `lib/index.js` 的文件头注释

## 它做什么（结论）

| 时机 | 行为 |
| --- | --- |
| 运行中（实时） | 事件驱动维护 `active-sessions.json`：会话在跑、名下有子代理在跑、有未结算后台作业、有定时任务、有 armed goal ⇒ 进表；全部消失 ⇒ 出表。写盘防抖 300ms |
| 崩溃 / 重启后 | 读表 → 两道闸门 → **先顶层、后子代理**逐条冷恢复唤醒（`resolveAgent` / `subagents.prompt`）→ 注入**固定首句 `sl已接续会话,继续` + 断点信息** → **唤醒成功即从表里移除** |
| 崩溃 / 重启后（子代理结果） | 子代理全部试完后，**按父会话汇总一条「子代理接续结果」通知**（✅已唤回 / ❌没能唤回+原因 / ⏸本次没尝试）；v0.7.2 起**成功也报**；v0.7.3 起父会话在跑就 **`steer` 插队**（正常情况下同轮可见）；v0.7.4 起**插队前先看 next-turn 是否清空**，没清空就排队（保顺序） |
| 重启前（可选） | 本机 `dsh-host-restart` 杀进程前调 `slHandoff.saveAll()`：**强制重算并落盘**（保证表反映的是那一刻的真实状态，而不是防抖窗口之前的）。该包**零改动** |

不做的事：不读会话文件、不渲染摘要、不写逐会话的记录文件、不注册任何斜杠命令或模型工具。

## 两条路径

```
实时（事件驱动）
  agent/status ────────────┐
  goal/activation-changed ─┤
  jobs.events.subscribe ───┼─► probeSessionWork(会话) ─► 有活？进表 : 出表
  周期兜底 30s ────────────┘         │                      │
                                    │                      └─► 防抖 300ms ─► 原子写 active-sessions.json
                                    └─ 判据三路并集（见下）

恢复（宿主启动，apply 后 4s）
  读表 → 闸门②(热加载?) → 等 sessionController → 闸门①(别的顶层会话在跑?) → 逐条：
    顶层    decideResume → resolveAgent（**冷恢复**：宿主读回完整历史 + 补 interrupted closer）
                        → followup(固定首句 sl已接续会话,继续 + 断点信息) → flush → **移除条目**
    父会话  **自己没有顶层条目**的父会话 → resolveAgent **先**冷唤醒（否则子代理注定失败、通知还自相矛盾）
            ⚠ 自己有条目的父会话不在这里处理（裸唤醒会让"让位"的那条永久丢掉续跑注入）
    子代理  decideSubagentResume(空会话⇒不可恢复 / 不在列表⇒让位) → 父 agent 活着
                        → subagents.prompt({mode:'continuable', delivery:'queue'})（宿主冷恢复）
                        → 成功/失败都记进"按父会话分组的结果"（成功也报）
  子代理全部试完 → 每个父会话一条通知(【sl 交接】子代理接续结果)：
                   在跑且 next-turn 已清空 ⇒ steer（next-step，正常情况下同轮可见）
                   其余（空闲 / next-turn 还压着消息 / 读不到 inbox）⇒ followup（next-turn，下一轮第一条）
  失败 ⇒ 条目留在表里，下次启动重试；不可恢复（空会话）⇒ 移除并写日志
  整批让位（热加载 / 别的会话在跑 / controller 等不到）⇒ 表一个字节都不动
```

## 注入文案（v0.7.2 起）

唤醒时注入的**首行是固定句** `sl已接续会话,继续`（半角逗号、`sl` 小写、无空格），
前面带 `INJECT_HEADING` 标记（`【sl 交接续跑】`）。固定首句之后是**继续指引**与**断点信息**。

**顶层会话**（`buildResumeText`）—— 完整示例：

```
【sl 交接续跑】sl已接续会话,继续

你的完整对话历史已经回来了 —— 先确认现状（文件、产物、作业输出），再决定从哪一步继续；不要照抄重启前的结论，重启后可能已有新进展。

重启时你名下还有这些在飞的活（会话历史里看不到，所以在这里告诉你）：
- 后台作业 bash-3：pwsh -Command 下载
- 子代理 session-child：补测试
- 定时任务 sch-1
- 自动续轮的目标（goal）还挂着：它本该继续自动往下跑
（上面这些子代理要等你这轮起来之后才逐个尝试唤回 —— 宿主要求父会话先活着；接续结果会另发一条消息告诉你。）
```

**子代理**（`buildSubagentResumeText`）—— 首句与顶层**逐字相同**，第二行补一句极简说明
（免得它把"接续"误当成"父代理新派的活"），随后是它必须知道的两件事：**挂在哪个父会话名下**、
**先汇报状态再继续**。完整示例：

```
【sl 交接续跑】sl已接续会话,继续
（你是子代理，这是重启后的接续，不是父代理新派活）

你挂在父会话 `session-parent` 名下。
你的完整对话历史已经回来了。请**先汇报当前状态**（做到哪一步、哪些结论已经有了、有没有留下半成品文件），再继续未完成的部分；不要照抄重启前的结论，重启后可能已有新进展。
```

说明几点：

- 「重启时你名下还有这些在飞的活」这一节**只在真的有断点信息时出现**（在跑的子代理 / 未结算作业 /
  定时任务 / armed goal）；`turn` 不列进去 —— 那是它自己的状态，不是"历史里看不到的活"。
- 那句**子代理预告**只在清单里**有子代理**时出现：子代理此刻还没被尝试唤回（见下节），
  不预告的话父会话会以为它们已经在跑，于是干等或重复派活。
- 正文超过 `resumeTextMaxChars`（默认 2000）时**截断**，并附一句"请用 read 工具确认现场后继续"。
- 子代理接续结果走**另一套文案**（`buildSubagentOutcomeNotice`），标题是
  `【sl 交接】子代理接续结果`，**故意不带** `【sl 交接续跑】` 前缀 —— 它是通知，不是续跑指令。

## 子代理接续结果通知（v0.7.2 新增，v0.7.3 起插队，v0.7.4 收紧条件）

**为什么是"事后"的另一条消息**：冷恢复一个子代理要求它的父 agent 此刻是 live 的，而父 agent
正是靠那条续跑注入才起来 ⇒ **续跑注入发出时，子代理一个都还没试过**（结果此刻不存在）。
所以结果只能在子代理全部试完之后补发，且**按父会话汇总成一条**（不是每个子代理刷一条）。

**为什么成功也报**（用户 2026-10-03 的要求）：父会话原先只能等子代理自己汇报，而它可能不汇报
（继续干活去了）—— 明确告诉它"已经唤回、接下来会自己向你汇报"，它才能既不干等、也不重复派活。

**v0.7.3 起"事后"不等于"等下一轮"**（用户 2026-10-03：「第二条注入太慢了，改成插队」）：
投递方式按父会话**当时的状态**选 —— 正在跑一轮 ⇒ `steer`（宿主 next-step 通道）；空闲 ⇒ `followup`
（next-turn，下一轮第一条）。宿主 `claim()` 每轮只从 next-turn 取 **1 条**，所以两条 followup 天然
是两轮 —— 这正是"慢"的根因。选路细节见 `pickOutcomeDelivery`。

**v0.7.4 起插队多一道闸**：`claim()` 是**先取全部 next-step、后取 1 条 next-turn**（宿主 `:104-105`），
所以 next-turn 里还压着没被取走的消息（续跑注入 / 用户消息 / goal 续轮）时插队会让结果跑到续跑指令
**前面** ⇒ 退回 `followup` 保顺序。判据是公开 getter `inbox.nextTurn` 为空；读不到 inbox（宿主形态
变动、projection 未注册）时同样退回 —— 顺序正确优先于"插队"这个优化。

**"同轮可见"有三个例外**（别把它当成保证）：① next-turn 没清空 ⇒ 排队（见上）；② 该轮被 **Stop /
abort** ⇒ 宿主把 steer 静默降级成 next-turn（`send()` 的 `wakingAfterAbort`，宿主 `:800-802`），
仍然会投、但等下一轮；③ 该轮以**非 abort 错误**结束（模型报错）⇒ 已入队的 next-step 没人取，
要等下一次外部唤醒（这一条对 followup 同样成立）。

完整示例（一个成功、一个失败、一个本次没尝试）：

```
【sl 交接】子代理接续结果（dsh 重启后自动唤回）

它们都挂在你（父会话 `session-root`）名下。

- ✅ `session-child-ok`：已唤回 —— 它接下来会自己向你汇报当前状态（若迟迟没动静，用 `send_message` 问一下）
- ❌ `session-child-bad`：没能唤回 —— 原因：投递给子代理失败：subagent/not-resumable（条目留在工作表里，本插件下次启动会再试一次）
- ⏸ `session-child-skip`：本次没尝试 —— 目标会话不在会话列表里（可能宿主刚启动、列表未装载完）（条目留在工作表里，本插件下次启动会再试一次）

没能唤回的那些：它们很可能已被重启打断，当时的结论可能**没有上报给你** —— 别把它们当成已经完成，也别当成还在跑。

下一步建议（挑一条）：
- 用 `send_message` 手动把它续起来（它的 id 就是上面那个），让它汇报到哪一步、再继续；
- 或者先确认现状（半成品文件、有没有改坏东西）后自己接手。
```

| 标记 | 状态 | 含义 | 条目还会再试吗 |
| --- | --- | --- | --- |
| ✅ | `resumed` | 已投递给宿主并冷恢复（它会自己向你汇报） | 已从表里移除 |
| ❌ | `failed` | 父会话唤不醒 / 服务缺席 / 投递抛错 | **会**（留在表里，下次 dsh 启动再试） |
| ❌ | `unresumable` | 明确不可恢复（**空会话**等） | **不会**（已从表里移除，文案里写明了） |
| ⏸ | `skipped` | 本次让位（**目标不在会话列表里**）或超出唤醒上限 | **会**（留在表里） |

说明几点：

- 逐条列出的上限是 `SUBAGENT_OUTCOME_MAX_LINES`（默认 8 条），超出的折叠成一行"还有 N 个没列出
  （原因见日志 `<绝对路径>`）"；每条的原因折叠成单行、截断 240 字符。
- **「没能唤回」那一段只在真有 ❌ 时出现**；全部成功时正文只有 ✅ 那几行（外加那句"迟迟没动静就
  `send_message` 问一下"的兜底）。
- **先唤醒父、再试子代理**（v0.7.3）：子代理条目可以独立于父条目存在，而"通知"和"投递"走的是同一个
  唤醒语义 —— v0.7.2 先判"父不是 live"、再靠通知把父唤醒，父收到的 ❌ 通知里会写着"原因：父会话 X
  此刻不是 live agent"，而它正是被这条通知叫醒的（评审 2026-10-03 实测复现）。现在阶段 1.5 先把这类
  父会话冷唤醒，子代理因此真的投得出去，原因也不再自相矛盾。
- **阶段 1.5 只碰"自己没有顶层条目"的父会话**（v0.7.4）：自己有条目的父会话该走阶段 1 的 `wakeRoot`
  （带判定、带续跑注入、成功即移除）。绕过它去裸唤醒会出两种事故（评审第二轮 P2）：父条目**让位**时
  它只收到一条结果通知，而 `markResumeDone` 之后跟踪器发现它没活就删掉条目 ⇒ **那条续跑注入永久丢失**；
  父条目是**空会话**时裸唤醒 + 投通知还会"凭空造出一个非空会话"。
- **预告与通知同源**（v0.7.4）：续跑注入里那句"接续结果会另发一条消息"看的是**工作表里有没有它的
  子代理条目**（与通知同一判据），不再看 activity 清单 —— 清单只来自宿主 waterfall，某个提供方缺席
  时会出现"没预告却发了通知"，父条目滞后一个 sweep 时会出现"有预告却没人发"。
- 通知的通道是 `sessionController.resolveAgent(父 id)` —— **唤醒语义**，父会话即使已经"死了"也会被
  冷唤醒后收到（用户 2026-09-28 拍板：宁可多起一轮也不漏通知）。连父会话都唤不醒时降级成日志，
  这一轮父会话确实不知情。
- 通知投递后按 **agent 对象** flush（与顶层注入同口径）；v0.7.2 按 id 查 live store，而刚冷恢复的父
  会话还没落库 ⇒ 稳定跳过 flush（评审 2026-10-03 实测），通知再遇一次崩溃就永久丢。
- 父会话 id 为空的子代理条目（手工改表才可能出现）跳过通知，只写日志。
- 插件在恢复途中被卸载（提前 return）时这一批不发 —— 进程都要走了，投递没有意义。
- **超出 `resumeMaxSessions` 上限而本次压根没试**的子代理条目：只在它的父会话**本次已经醒着**时补一条
  ⏸ 说明（不额外唤醒任何会话，否则等于绕过上限）；否则不出现在通知里。默认上限是 0（不限）。

## 判据：三路并集

判定「这个会话此刻有没有在飞的活」时，**三路都跑、取并集**（谁在场谁出力）：

| 来源 | 覆盖 | 依据 |
| --- | --- | --- |
| 宿主活动 | `turn` / `job` / `subagent` / `schedule` | `ctx.waterfall('workspace/session-activity', {sessionId}, () => [])` —— 与宿主归档判定**逐字同一条调用**（`dsh-workspace/lib/index.js:529`）。返回的 `items` 就是断点信息（哪个作业、哪个子代理） |
| 自建判据 | `turn` / `subagent` / `job` | `agent.status === 'running'`；血缘子代理在跑（沿 `header.parentSession` 上溯）；`jobs.list()` 里 `owner` 精确匹配且 `running`/`stopping` |
| 单独查 | `goal` | `goals.get(agent)` 的 `phase === 'active'` 且 `activation === 'armed'` |

**为什么不是「主路径 + 回退」**：`workspace/session-activity` 的提供方是**逐个可选**的
（`dsh-agent` 报 turn、`dsh-jobs` 报 job、`dsh-subagent` 报 subagent、`dsh-schedule` 报 schedule
各自注册），而"某个包没装载、少了一类"与"那一类没有活"在返回值上**同形**（waterfall 无人应答时
返回默认值 `[]`）。拿它当唯一答案就会漏判，所以自建判据始终参与。

> ⚠ 曾经按"探测 `ctx.get('workspace')` 判断体系在不在场"实现过，**那是错的**：那个服务的真名是
> `workspaceRegistry`，而且它只是这个 waterfall 的**发起方**，与"有没有人应答"无关。

`goal` 不在宿主的 `SessionActivityKindMap` 里（那里只有 turn/job/subagent/schedule），
所以单独查。为什么 armed goal 算「有活」：它由 `goal-round-driver` 在会话空闲时自动续轮，
重启打断它 = 断了一条在飞的链。

## 为什么这么设计（宿主已经提供了什么）

v0.6.0 是**快照式**的：人敲 `/sl` 或重启插件在杀进程前保存，那一刻把每个会话渲染成一份
2~4 KB 的 Markdown 摘要。它有三个固有缺口：**保存时机离散**（崩溃/断电时没人来得及保存）、
**摘要有损**（只有最近 5 条用户目标 / 3 条进展 / 6 条工具调用）、**快照会过期**（保存后、
重启前新起的工作不在里面）。

v0.7.0 把这三条一起解掉，靠的是认清宿主**已经**提供了什么（本机源码逐条核实）：

1. **会话内容宿主已经实时落盘**（`dsh-session-persistence-jsonl` + checkpoint 策略）。
   插件的"保存会话内容"是重复劳动 —— 真正缺的只有"谁有没做完的事"这一张表。
2. **冷恢复会把完整历史读回来**：`sessionController.resolveAgent(id)` → `resumeObserved` →
   `ctx.agents.resume({resumeSessionId})` → `agentLoop.resumeWith` → `handle.read(0, undefined)`
   冷读整份日志 → 重建 Agent（`dsh-api-session-controller/lib/index.js:399-411`、
   `dsh-agent-loop/lib/index.js:1912-1955`）。所以唤醒时**不需要注入摘要**。
3. **宿主还会自动修「崩溃孤儿轮」**：冷恢复时 `interruptedTurnClosers(persisted)` 给日志尾部
   那个未闭合的 turn 补 `turn/end{reason:{kind:'interrupted'}}`
   （`dsh-agent-loop/lib/index.js:1935-1936`、`dsh-session/lib/types/repair.js:154`）。
   这就是"复跑"的宿主原生支持 —— 也是**注入一条固定首句 + 继续指引**就够的原因。
4. **宿主有统一的「会话活动」查询接口**（上表第一行）。

于是插件只需要：维护一张表 + 在启动时按表唤醒。

## 工作表格式

位置：`<DSH_HOME>\storages\sl-handoff\active-sessions.json`（`DSH_HOME` 默认 `~\.dsh`，即 `%USERPROFILE%\.dsh`）。
**不写用户工作区**。原子写（`.tmp-` + rename），写盘防抖 300ms；**表为空时删除文件**（"没有文件"就是"没有待办"）。

```json
{
  "version": 1,
  "updatedAt": 1759048200000,
  "items": [
    {
      "sessionId": "session-aaaa1111-2222-3333-4444-555555555555",
      "kind": "root",
      "parentSessionId": "",
      "title": "实现 dsh-host-sl 插件",
      "cwd": "<工作区>",
      "why": ["turn", "job"],
      "goal": false,
      "activity": [
        { "kind": "turn" },
        { "kind": "job", "items": [{ "id": "bash-3", "label": "pwsh -Command 下载" }] }
      ],
      "since": 1759048100000,
      "updatedAt": 1759048200000
    }
  ]
}
```

| 字段 | 含义 |
| --- | --- |
| `kind` | `root` \| `subagent` —— 恢复侧据此选投递路径；**缺失或形态不符一律按 `root`**（安全侧：绝不当成子代理） |
| `parentSessionId` | 子代理的**直接父**会话 id（`session.header.parentSession`），投递时必需。必须是直接父 —— 宿主的 `authorizeLineage` 会校验 `parentSession === parent.id`，写祖先会被拒 |
| `why` | 命中哪几条判据（固定顺序 `turn` / `subagent` / `job` / `schedule` / `goal`），排障用 |
| `activity` | 宿主活动返回的原始项（断点信息的来源：作业 id/label、子代理 id/label） |
| `goal` | 是否有 armed goal |
| `since` / `updatedAt` | 首次进表时间 / 最后一次刷新时间 |

**表里只有"此刻有活"的会话**：空闲会话不在表里 ⇒ 崩溃后不唤醒它（延续 v0.5.1 的口径）。
**陈旧上限 24h**：超过这个年龄的表不消费（"崩溃很久之后才重启"，唤醒它没有意义），旧文件保留不动。

## 服务契约（`slHandoff`）

`ctx.provide` 提供，**同名同形兼容**本机 `dsh-host-restart`（那个包因此零改动）。
消费者**不要**把它写进 `inject`（那样本插件缺席时消费者整个不 apply）；用 `ctx.get('slHandoff')` 可选读取。

| 方法 | 行为 |
| --- | --- |
| `saveAll(options?, note?)` | **强制重算所有 live 会话的活动状态并立即落盘**。幂等、同步返回、从不抛。`dsh-host-restart` 在杀进程前调它 ⇒ 保证表反映的是那一刻的真实状态。`note` / `noteSessionId` / `session` 参数**保留但不使用**（v0.7.0 不再写"下一步说明"）。返回 `{ok, saved, failed, items, message, createdAt, activeFile}`；`items[].file` 给的是**工作表路径**（消费者用它拼"存到哪了"，代价是同一路径会列 N 遍） |
| `pendingSummary()` | 工作表摘要：`{exists, reason?, items:[{sessionId, kind, done, active, wake}]}`。表里的条目一律 `done:false / active:true / wake:true`（"在表里"就等于"待唤醒"）。消费者用它判断"这次重启的续跑消息该由谁注入" |
| ~~`save(sessions, note?)`~~ | **已删除**（新模型下"保存谁"由活动状态决定，不由调用方指定） |

服务随**提供它的 fiber** 卸载自动注销（`ctx.provide` 内部就是 `fiber.effect`）。

## 配置项（插件 config，一般不用动；测试靠它隔离）

| 键 | 默认 | 说明 |
| --- | --- | --- |
| `home` | `$DSH_HOME` 或 `~\.dsh` | 数据根 |
| `storageDir` | `<home>\storages\sl-handoff` | 落盘目录 |
| `activeFile` | `<storageDir>\active-sessions.json` | 工作表路径 |
| `logFile` | `<storageDir>\sl-handoff.log` | 日志路径（**配置解析失败时**退到 `DSH_SL_LOG_FILE` 或 `<home>\storages\sl-handoff\sl-handoff.log`） |
| `debounceMs` | `300` | 写盘防抖：状态翻转合并这么久再落盘（崩溃最多丢这个窗口） |
| `sweepMs` | `30000` | 周期兜底重算（防漏事件；作业事件订阅失败时也靠它） |
| `staleMs` | `86400000`（24h） | 表的新鲜度上限，超时表不消费 |
| `bootDelayMs` | `4000` | apply 后延迟多久开始恢复（避开启动风暴） |
| `controllerWaitMs` | `30000` | 等 `sessionController` 出现的上限 |
| `bootGraceMs` | `300000`（5min） | 闸门②：进程运行超过它就判定为热加载、不唤醒 |
| `resumeTextMaxChars` | `2000` | 注入正文上限（固定首句 + 继续指引 + 断点信息，不需要很长） |
| `resumeMaxSessions` | `0`（**不限**） | 一次启动最多唤醒多少条；`>0` 时其余**留在表里**，下次启动继续 |
| `requireColdAgent` | `false` | `true` 时额外要求目标会话 `agentAvailable === false`（目标侧唯一剩下的让位理由） |

非法值 **fail loud**（抛错）—— 由 `apply` 的外层 try/catch 接住，降级并写日志，不会拖垮宿主。

## 怎么装

### 三处装载入口（缺一不可）

1. **包内** `cordis.patch.yml`：含 `- insert: - id: sl-handoff / name: 'dsh-host-sl'`（行 id 是插件页行级开关的寻址键，**勿改**）；
2. **包** `package.json`：`dsh.bundle.patch: ./cordis.patch.yml`，且 `files` 白名单含 `cordis.patch.yml`；
3. **profile** `package.json` 的 `dsh.profile.bundles` 里要有包名 `dsh-host-sl`。

本包**不声明 `peerDependencies`**：它一个宿主包都不 import（理由见下），兼容性闸门直接放行。

### 安装（从 GitHub 装）

本包**没有发布到 npm 注册表**，装法就是"让 profile 能解析到它"。`dsh plugin` 的参数**透传给 pnpm**，
所以任何 pnpm 支持的 spec 都能用；最常用的两条：

```powershell
# ① 直接从 GitHub 装（推荐；把 <profile> 换成你的 profile 名，例如 desktop）
dsh plugin --profile <profile> add github:liuyun847/dsh-host-sl

# ② 或者先克隆、再以本地目录装（想改代码时用这条）
git clone https://github.com/liuyun847/dsh-host-sl.git
dsh plugin --profile <profile> add file:./dsh-host-sl
```

装卸时请先把 dsh **完全退出**，装完再启动（`dsh plugin` 在底层跑 `pnpm add/remove`，会改 profile 的
`node_modules`）。装完核对两处：profile 的 `package.json` 里 `dependencies` 有 `dsh-host-sl`，
且 `dsh.profile.bundles` 数组里有包名 —— **后者缺了插件不会加载**（见上面的「三处装载入口」）。
已知 `dsh plugin` 在 pnpm 中途被杀时会漏写/残留 `bundles`，手工补一行即可（顺序无要求）。

> 若你另有本地装卸 CLI（例如 `dshpm`），它同样可用：把 spec 换成
> `dshpm add github:liuyun847/dsh-host-sl --profile <profile>` —— 与 `dsh plugin` 的区别只是
> **无论 pnpm 成败，它都会用之后实际的文件状态重新校正 `dsh.profile.bundles`**。

### 生效与重载

**装完（或改完代码）一律要重启 dsh 才生效**：新增插件虽然会因 profile `package.json` 变更触发重组合，
但 `lib/*.js` 按模块 URL 缓存，进程里跑的还是旧代码。

> **两条硬约束（实测）**
>
> - **改"保存侧"要重启两次**：改 `lib/*.js` 后，**第一次重启仍由内存里的旧代码执行保存侧**
>   （写表 / `saveAll`），那次写出的表是旧代码写的 ⇒ 保存侧改动（含表格式变化）验收要重启**两次**。
>   **只改"唤醒侧"（读表 → 注入 → 通知，v0.7.2 起的几版都是）时一次重启就够** ——
>   新进程一启动加载的就是新代码，唤醒发生在 apply 后 4s，跑的必然是新的。
> - **`link:` 与 `file:` 不一样**：`link:` 是联结（Junction），源码目录即运行副本，改完**不需要**重装、
>   重启即可；`file:` 是拷贝，改完源码要重新 `add` 一次（或干脆改用 `link:`）。

### 卸载

```powershell
dsh plugin --profile <profile> remove dsh-host-sl
# 数据目录（工作表 + 日志）一并删掉；$env:USERPROFILE\.dsh 即 ~/.dsh
Remove-Item -Recurse -Force "$env:USERPROFILE\.dsh\storages\sl-handoff"
```

卸载后没有残留：不改任何 profile 文件、不写用户工作区、不起进程、不留后台任务
（事件订阅与定时器都在 `ctx.effect` 的清理函数里撤销）。

## 从 v0.6.0 升级

- **`/sl` 命令已删除**：斜杠菜单里不再有它，这是有意的（自动化之后不需要人敲）。
- **旧文件不再被消费**：`pending.json` 与 `handoff-*.md` 与新机制无关，**不迁移、不删**
  （记录文件是审计线索，留着）；新机制只看 `active-sessions.json`。
- **`slHandoff.save()` 已删除**：消费者若调它要改用 `saveAll()`（本机 `dsh-host-restart` 本来就只用 `saveAll` + `pendingSummary`，无需改动）。
- **"下一步说明"没有了**：v0.6.0 靠 `/sl <说明>` 或重启工具的 `note` 写进记录；v0.7.0 不再写
  （用户拍板：说明留空）。恢复时的方向由模型读自己的完整历史自行判断。

| `作业事件订阅不可用（…）—— 作业变化靠周期兜底` | `jobs` 服务缺席或没有 `events.subscribe` ⇒ 降级，不致命 |
| `启动时没有活跃工作表（首次运行或上次正常退出）` | 上次是正常退出（表被清空了）或首次运行 |
| `活跃工作表已加载：N 条待唤醒（顶层 a / 子代理 b，表龄 Ns）` | 上次崩溃留下了待办 |
| `活跃工作表判定为 stale/invalid，不消费（旧文件保留不动）` | 表太旧/损坏 |
| `会话 <id> 有在飞的活（turn+job）⇒ 写入工作表` | 进表（只在"新出现 / 判据组合变了"时写，避免刷屏） |
| `会话 <id> 已无在飞的活 ⇒ 从工作表移除` | 出表 |
| `无法判定会话 <id> 有没有在飞的活（…）⇒ 按"有活"处理` | 保守方向：判不了就多唤醒一次 |
| `会话 <id> 的宿主活动查询不可用（…）⇒ 只靠自建判据` | 宿主活动那一路降级，自建判据照常 |
| `恢复判定：yield —— …（表保留，下次启动再判）` | 让位（热加载 / 别的顶层会话在跑） |
| `唤醒成功：顶层 <id> —— …（已从工作表移除）` | 单条唤醒成功 |
| `唤醒失败（留在工作表里，下次启动重试）：…` | 单条失败（fail-soft，不影响其它条目） |
| `父会话 <id> 此刻不是 live agent（冷恢复子代理要求 exact live parent）` | 子代理恢复不了。v0.7.3 起阶段 1.5 会**先**冷唤醒这类父会话，所以这行只在"父会话连 `resolveAgent` 都唤不醒"时出现（上一行会有 `的父会话 <id> 唤不醒（…）`） |
| `子代理接续结果已通知 父会话 <id>（steer 插队，同轮可见；已唤回 a / 共 b 条；落盘=ok）` | 父会话**正在跑一轮且 next-turn 已清空** ⇒ 通知走 next-step 插队（v0.7.3 起） |
| `子代理接续结果已通知 父会话 <id>（followup 排队，下一轮可见；已唤回 a / 共 b 条；落盘=ok）` | 父会话**空闲**、或 next-turn 里还压着消息（v0.7.4 的闸）、或读不到 inbox ⇒ 退回 next-turn 排队（保证"先续跑注入、后结果"的顺序）。`已唤回 a` 是其中成功的条数 |
| `父会话 <id> 的 N 条子代理接续结果发不出去（…）—— 只写日志` | 连父会话都唤不醒 ⇒ 这一轮它确实不知情（不重试，也不写标记） |
| `子代理 <id> 的父会话 <id> 先冷唤醒（子代理这样才投得出去）` | 阶段 1.5：**自己没有顶层条目**的父会话被提前唤醒（v0.7.3 起） |
| `子代理 <id> 的父会话 <id> 自己在工作表里有条目（本批已判过或超上限）⇒ 不裸唤醒它（裸唤醒会让它只收到通知、丢掉续跑注入）` | 阶段 1.5 主动跳过（v0.7.4）：这种父会话该由阶段 1 处理，裸唤醒会让"让位"的那条永久丢掉续跑注入 |
| `子代理 <id> 的父会话 <id> 唤不醒（…）—— 该子代理注定失败` | 阶段 1.5 失败：该子代理必然投不出去，结果通知也会降级成日志 |
| `子代理 <id> 没有 parentSessionId ⇒ 接续结果没有可通知的父会话（只写日志）` | 手工改表才可能出现；正常路径下子代理条目一定带直接父 id |
| `本次恢复结束：唤醒成功 a 条 / 失败 b 条（其中让位 c 条、明确不可恢复 d 条）… ⇒ 工作表剩 N 条` | 一批的收尾汇总 |
| `有 N 条唤醒成功但 flush 未成功` | 注入已入队但可能没落盘；会话历史本身在磁盘上，必要时手动发一条消息续上 |
| `apply 抛错，插件已降级（…）` | 兜底：配置非法等。**apply 绝不把异常抛回 loader** |

常见现象与处置：

| 现象 | 多半是什么 |
| --- | --- |
| 重启后什么都没唤醒 | ① 上次是**正常退出**（没有活 ⇒ 表本来就是空的）；② 崩溃前那些会话已经空闲（空闲不进表）；③ 表被判成 stale/invalid（日志有专行） |
| 唤醒了一部分 | 看 `本次恢复结束` 与随后的失败行：失败的条目**留在表里**，下次启动重试 |
| 某个会话被漏掉了 | 它当时可能**不在 live agent 表里**（从没被任何客户端订阅过 ⇒ 插件看不到它）；或 `agents.list()` 那次枚举失败（日志有 `无法判定…`） |
| 子代理没被唤回 | 常见原因（日志各有专行）：① 父会话连 `resolveAgent` 都唤不醒（v0.7.3 起阶段 1.5 会先试一次）；② `subagents` 服务不可用；③ 投递给子代理失败（原因带在消息里，例如 `subagent/not-resumable`）；④ 目标不在会话列表里（⇒ ⏸ 让位）或它是空会话（⇒ ❌ 不再重试）。**可重试的条目留在表里**，下次启动再试；**它的父会话会收到一条「子代理接续结果」通知**（成功也报，❌/⏸ 都在里面） |
| 结果通知要等很久才看到 | 看日志那行是 `steer 插队` 还是 `followup 排队`：**排队**只有三种情形 —— 父会话空闲（`followup` 自带唤醒，它立刻起一轮，其实是最快路径之一）、next-turn 里还压着别的消息（v0.7.4 的保顺序闸）、读不到 inbox。父会话**在跑**却排队，先看是不是这三种之一 |
| 想让某个空闲会话也被唤醒 | 表里没有它 = 它保存那一刻没有在飞的活。要它被唤醒，就让它**真的有活**（跑一轮、派个子代理、挂个后台作业、起一个 armed goal）；也可以手工把它的条目加进 `active-sessions.json`（`why` 随便填，恢复侧不看这个字段） |
| 表里有个会话，但它其实没活了 | 周期兜底最多滞后 `sweepMs`（30s）；或它不在 live 表里（跟踪器不删这类条目 —— 那是"上次崩溃留下的待办"） |
| 插件整包加载失败、dsh 起不来 | 本包零宿主依赖、apply 全兜底，理论上不会；真出现就看 dsh 自己的 stderr（`<工具目录>\dsh-watchdog-dsh.log`） |

## 已知限制

- **恢复 ≠ 无损**：冷恢复是"带着完整历史重起一轮"，**被打断的那一刻正在执行的那一步工具调用会丢**
  （宿主没有重放机制，工具调用也不幂等）。注入正文因此明说"先确认现状再继续"（固定首句
  `sl已接续会话,继续` 之后的继续指引就是这句话）。
- **崩溃最多丢 300ms 的状态翻转**（写盘防抖窗口）。这段时间内刚起的工作不会被记录 ⇒ 不会被唤醒。
- **作业事件订阅失败时靠 30s 周期兜底**：`jobs.events.subscribe` 缺席（服务形态变动）时，
  作业的起停最多滞后一个 sweep 周期。
- **空闲会话不进表 ⇒ 不唤醒**（用户 2026-09-29 拍板的口径延续）：一个会话跑完一轮后停在那里
  等用户回话，它不算"有活"。要它被唤醒，得让它真的有活（见排障表）。
- **只覆盖被 promote 成 live agent 的会话**：从没被任何客户端订阅过、也没被 promote 的会话
  不在 `agents.list()` 里 ⇒ 插件看不到它（对本机 Web 场景没影响 —— 打开过的会话都会被订阅）。
- **唤醒是"排进下一轮"，不是立刻执行**：`followup` 的语义是入队 + 驱动新一轮，不打断当前轮。
  目标会话正在跑时，触发消息等它那一轮结束才被取走。
- **续跑注入与子代理结果通知是两条消息**（v0.7.2）：子代理的结果只能在它们全部试完之后才知道，
  那时续跑注入早已发出（时序硬约束见上）。v0.7.3 起通知走 `steer` **插进父会话当前轮**
  （next-step），所以不必等下一轮；**例外有三种**（v0.7.4 起）：父会话当时空闲、next-turn 里还压着
  别的消息（保顺序）、读不到 inbox —— 这三种都退回 `followup` 排队。
- **`steer` 不打断正在进行的模型调用**：它插在**下一次模型调用之前**（宿主 next-step 语义），
  且 next-step 非空时那一轮不会结束，所以正常情况下消息一定会被看到（代价是父会话那一轮多走一步）。
  ⚠ **不是保证**：该轮被 Stop/abort 时宿主会把 steer 降级成 next-turn（宿主 `:800-802`）；该轮以
  非 abort 错误结束时已入队的 next-step 没人取（`:856` 不置 `wakeRequested`、`:898` 不补投），
  要等下一次外部唤醒 —— 后者对 `followup` 同样成立。
- **子代理结果通知不重试**：父会话连 `resolveAgent` 都唤不醒时，这一轮它确实不知情（只写日志）；
  与"失败条目留在表里下次再试"不同 —— 下次启动时会重新试唤回子代理，结果也会重新回报。
- **嵌套子代理（孙代理）的收件人是它的直接父会话**，而那可能是一个**子代理会话**：通知会直接
  用 `followup`/`steer` 投给它（不经 `subagents.prompt`），中间层不会额外收到汇总。协调者场景里
  顶层才是最终读者，这条语义**未做特殊处理**（评审 2026-10-03 列为 P3，已知即可）。
- **闸门① 仍在**：批次开始时若有**别的**顶层会话正在跑一轮，整批让位（表一个字节不动）。
  "别的"= 不在本批唤醒名单里的会话 —— 所以"父会话在跑"本身不构成让位理由（它在本批里）。
- **`/sl` 没了 ⇒ 没有"人主动存档"的入口**：想留档就在有活的时候让它跑着（表会记录），
  或者手工往 `active-sessions.json` 里加条目。
- **`goal` 是单独查的**：宿主的活动体系里没有这一类，所以它的判据由本插件自己维护
  （读法照抄 `dsh-host-goal-subagent-gate`）。

## 真机验收（协调者执行，需用户同意）

1. 按「怎么装」确认已以 `link:` 装进 **desktop** profile（web 那份退役保留，不必动）。
2. **第一次重启**（让新代码进内存）：重启后看日志有没有 `apply: v0.7.4 …` —— 没有就是包没被加载。
3. **第二次重启**（端到端）：
   - 重启前让某个会话**有活**（跑一轮、或派个子代理、或起个后台作业）；
   - 走 `restart_dsh` 重启 ⇒ 日志里应出现 `重启前已保存会话交接记录…`（来自 `dsh-host-restart`，
     它会调 `saveAll`）与 `活跃工作表已提交：N 个会话…`；
   - 新进程起来后看 `~\.dsh\storages\sl-handoff\sl-handoff.log`：
     `活跃工作表已加载：N 条待唤醒` → `唤醒成功：顶层 <id> …（已从工作表移除）` →
     `本次恢复结束：唤醒成功 N 条 … ⇒ 工作表剩 0 条`；
   - 被唤醒的会话里应出现一条以 `【sl 交接续跑】sl已接续会话,继续` 开头的用户消息，
     且**带断点信息**（当时在跑的子代理 / 未结算作业）；清单里有子代理时还应带那句**预告**。
4. **子代理接续结果验收**（v0.7.2 新增、v0.7.3 改成插队，最容易漏的一环）：
   - 重启前让某个会话**派一个子代理并让它跑着**（子代理条目会进表）；
   - 重启后除了续跑注入，该父会话里还应**再**出现一条以 `【sl 交接】子代理接续结果` 开头的用户消息：
     成功时是 `- ✅ \`<子代理 id>\`：已唤回 —— 它接下来会自己向你汇报当前状态（若迟迟没动静…）`，
     失败时是 `- ❌ …：没能唤回 —— 原因：…`；
   - 日志里对应 `子代理接续结果已通知 父会话 <id>（steer 插队，同轮可见；已唤回 a / 共 b 条；落盘=ok）`
     —— **`steer 插队` 是 v0.7.3 起的判据**（父会话被唤醒后就在跑那一轮、next-turn 已清空，所以走插队）；
     看到 `followup 排队` 先看是不是三种合法情形（父会话空闲 / next-turn 还压着消息 / 读不到 inbox）；
   - **插队的验收点**：那条通知**不该等到下一轮**才出现 —— 父会话第一轮的工具调用之后就会看到它
     （同一轮的下一步），而不是等整轮结束再开一轮；
   - **v0.7.4 的两条判据**：① 父会话自己有条目且让位时，日志应有
     `自己在工作表里有条目（本批已判过或超上限）⇒ 不裸唤醒它`，且**不该**出现
     `先冷唤醒（子代理这样才投得出去）`；② 表里若有"父条目 + 子代理条目"两条且父被正常唤醒，
     续跑注入里应带那句预告（预告看的是表里的子代理条目）；
   - ⚠ **成功也报**：子代理唤回成功时也必须看到那条 ✅ 通知 —— 只看到失败通知说明还在跑旧代码。
5. **崩溃兜底验收**（可选，最有说服力）：让某个会话有活，然后**硬杀** dsh 进程
   （任务管理器 / `Stop-Process`，不走重启工具）⇒ 看门狗拉起新进程 ⇒ 看上面那几行日志是否照样出现。
   这一轮**没有 `dsh-host-restart` 参与**，纯靠实时工作表唤醒。
6. **空闲不唤醒验收**：让一个会话跑完一轮后停在那里（不要动它），然后重启 ⇒ 它**不该**被唤醒
   （表里没有它），日志里也不该有它的 `唤醒成功` 行。
